The Python package speaks the same wire protocol as the TypeScript adapters and connects to the
same `graphmind` CLI, so a Python agent and a TypeScript one look identical in the viewer.

```sh
pip install graphmind-ai
```

- **Distribution name** `graphmind-ai`, **import name** `graphmind`.
- **Python 3.10+**, one runtime dependency (`websockets`), MIT licensed.
- Provider SDKs are optional extras: `pip install 'graphmind-ai[openai]'`, `[anthropic]`,
  `[langchain]`, or `[all]`.

The API is idiomatic Python rather than a transliteration: a context manager for runs, a
decorator for tools, and one `instrument_*` call per client. Everything below has a module-level
form (`import graphmind as gm`, then `gm.tool`) and an instance form
(`gm = graphmind.init(...)`, then `gm.tool`) — `init` sets the process-wide default, so the two
refer to the same session and can be mixed freely.

## End to end (OpenAI)

```python title="support_agent.py"
import json
import graphmind
from openai import OpenAI

gm = graphmind.init(app="support-agent")

# 1. Instrument the client — every request becomes a gated llm:step node.
client = graphmind.instrument_openai(OpenAI())


# 2. Decorate your tools — each call becomes a gated tool node.
@gm.tool
def search_orders(email: str):
    return db.orders.find(email=email)


@gm.tool
def issue_refund(order_id: str, cents: int):
    return payments.refund(order_id, cents)


TOOLS = {"search_orders": search_orders, "issue_refund": issue_refund}

TOOL_SPECS = [
    {
        "type": "function",
        "name": "search_orders",
        "description": "Find a customer's recent orders",
        "parameters": {
            "type": "object",
            "properties": {"email": {"type": "string"}},
            "required": ["email"],
        },
    },
    {
        "type": "function",
        "name": "issue_refund",
        "description": "Refund an order",
        "parameters": {
            "type": "object",
            "properties": {"order_id": {"type": "string"}, "cents": {"type": "integer"}},
            "required": ["order_id", "cents"],
        },
    },
]


def main():
    # Wait for the debugger handshake so gates are armed from the first event.
    gm.ready()

    # 3. Open a run — everything inside belongs to it.
    with gm.run("handle-ticket"):
        messages = [
            {"role": "user", "content": "Order #4471 arrived broken. Sort it out."}
        ]

        for _ in range(8):
            response = client.responses.create(
                model="gpt-5.4", tools=TOOL_SPECS, input=messages
            )

            calls = [item for item in response.output if item.type == "function_call"]
            if not calls:
                print(response.output_text)
                break

            messages += response.output
            for call in calls:
                result = TOOLS[call.name](**json.loads(call.arguments))
                messages.append({
                    "type": "function_call_output",
                    "call_id": call.call_id,
                    "output": json.dumps(result),
                })

    gm.dispose()


main()
```

Run `graphmind` in one terminal, `python support_agent.py` in another.

`instrument_openai` patches `chat.completions.create` (and `.parse`) and `responses.create` **on
the instance** — no library monkey-patching, no import hooks. It is idempotent, and clients
created *after* the call are not instrumented, so call it on each client you build. Streaming
responses are teed: your code receives exactly the provider's stream while GraphMind observes the
deltas. A `tools=[...]` argument is pre-announced as a `graph.hint`, so the viewer draws the tool
roster grey before anything runs.

`.with_raw_response.create(...)` and `.with_streaming_response.create(...)` are covered too,
whether you touched them before or after instrumenting: one node per call, and your code still
gets the SDK's own raw response object. With `stream=True`, the event stream `.parse()` returns is
teed, so text and final usage land on the node. For `with_streaming_response` the request (and
the `before` gate) happens in `__enter__`.

An injected reply comes back as the type the call returns — `ChatCompletion`,
`ParsedChatCompletion` or `Response` — not a dict. Type a bare string (it becomes a one-message
assistant reply) or an object with that type's fields; missing ids, timestamps and the `model`
are filled in, and for `chat.completions` a bare message such as `{"content": "..."}` or
`{"tool_calls": [...]}` works too. A payload that cannot be rebuilt is handed back unchanged, with
one warning.

## Anthropic

Swap one line:

```python
import anthropic
import graphmind

gm = graphmind.init(app="support-agent")
client = graphmind.instrument_anthropic(anthropic.Anthropic())

with gm.run("handle-ticket"):
    message = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=1024,
        tools=TOOL_SPECS,
        messages=messages,
    )
```

Everything else — `@gm.tool`, `gm.run`, `gm.ready` — is identical.

`messages.parse` and `messages.stream` are instrumented too, and so are the same three methods on
`client.beta.messages`. For `.stream` the HTTP request happens in `__enter__`, so that is where
the gate holds, and the proxy observes both consumption styles (raw event iteration and
`.text_stream`). It is the one *provider* attachment point where `inject` and `retry` are
unavailable: GraphMind cannot fabricate a provider stream object, so it holds, warns, and
continues rather than lying about having substituted one. Elsewhere an injected reply comes back
as a `Message` (`BetaMessage` on `beta.messages`, the `Parsed*` type from `.parse`), built from a
string or an object with the type's fields; its `usage` is zero unless you give one.

## OpenAI Agents SDK and Pydantic AI

Both build on the provider SDKs, so you instrument the client and hand it to the framework.

```python
import graphmind as gm
from agents import set_default_openai_client
from openai import AsyncOpenAI

# OpenAI Agents SDK: it builds its own AsyncOpenAI unless you set a default.
set_default_openai_client(gm.instrument_openai(AsyncOpenAI()))
```

```python
from anthropic import AsyncAnthropic
from openai import AsyncOpenAI
from pydantic_ai.providers.anthropic import AnthropicProvider
from pydantic_ai.providers.openai import OpenAIProvider

# Pydantic AI: pass an instrumented client to the provider, and the provider to your model.
openai_provider = OpenAIProvider(openai_client=gm.instrument_openai(AsyncOpenAI()))
anthropic_provider = AnthropicProvider(anthropic_client=gm.instrument_anthropic(AsyncAnthropic()))
```

The package's tests prove the client side, not the frameworks, which they do not install: the
calls these frameworks make are recorded and gated, and an injected reply is the type they read.

| Framework path | Client call | Tested |
| --- | --- | --- |
| Agents SDK `Runner.run` | `responses.create` | node, gates, typed `Response` inject |
| Agents SDK `Runner.run_streamed` | `responses.with_streaming_response.create(stream=True)`, read via `.parse()` | node with text + usage, `before` gate in `__enter__`, one node per call in either access order |
| Pydantic AI, OpenAI models | `responses.create` / `chat.completions.create` | node, gates, typed `Response` / `ChatCompletion` inject |
| Pydantic AI, Anthropic models | `beta.messages.create`, with and without `stream=True` | node, gates, typed `BetaMessage` inject |

Inject into non-streamed runs (`Runner.run`, `agent.run`); streamed ones are in
[Known limits](#known-limits). Tool calls these frameworks make are not nodes by themselves.

## LangChain / LangGraph

Attach a callback handler — the sync one for sync chains, the async one for `ainvoke` and
LangGraph:

```python
import graphmind
from langgraph.prebuilt import create_react_agent

gm = graphmind.init(app="support-agent")
gm.ready()


# Decorate the tools to get inject and retry — the handler alone cannot do those.
@gm.tool
def search_orders(email: str) -> list[dict]:
    """Find a customer's recent orders."""
    return db.orders.find(email=email)


# LangChain builds its schema from the decorated function's name, docstring and
# signature, all of which `@gm.tool` preserves — so hand it the wrapper directly.
agent = create_react_agent(model, tools=[search_orders, issue_refund])

with gm.run("handle-ticket"):
    result = agent.invoke(
        {"messages": [{"role": "user", "content": "Order #4471 arrived broken."}]},
        config={"callbacks": [gm.handler()]},
    )

gm.dispose()
```

```python
# async graphs / LangGraph — use the async handler
await gm.ready_async()
result = await agent.ainvoke(payload, config={"callbacks": [gm.async_handler()]})
```

Chains, LLM calls, chat models, tools and retrievers each get their own node kind, and
LangChain's `parent_run_id` becomes the parent/child structure on the canvas.

| LangChain concept | node kind | node id |
| --- | --- | --- |
| chain / runnable | `chain` | `chain:<name>` |
| LLM / chat model | `llm` | `llm:<name>` |
| tool | `tool` | `tool:<name>` |
| retriever | `retriever` | `retriever:<name>` |

<Aside type="caution" title="Callbacks pause; they cannot inject">
LangChain callbacks are **observers**: the framework ignores a handler's return value, so nothing
in a callback can substitute a chain's result. GraphMind accepts `inject` and `retry` at a
callback-only gate, warns once naming the wrapper you need, and treats them as `continue`. It
never pretends to have substituted something.

Pausing, on the other hand, genuinely works: sync callbacks are invoked inline on the executing
thread and async ones are `await`ed, so blocking there really does stop the clock. To *change* a
result, wrap the call site — `@gm.tool` / `gm.wrap_tools` on the tool function, or `gm.span`
around the code you want to be able to replace.

A *sync* handler inside an *async* chain still holds (it is dispatched to the default executor
and awaited), but it parks a thread-pool thread per concurrent run — prefer
`gm.async_callback_handler()` there.
</Aside>

## Anything else: spans

For the parts of a graph GraphMind cannot see by itself — a LangGraph node body, a hand-rolled
planner loop, a retrieval step in your own framework:

```python
with gm.span("plan", kind="chain") as span:   # `async with` too
    plan = build_plan(state)
    span.set_output(plan)
```

A span has a `before` gate and honours `abort`. It owns no return value, so an injected value is
surfaced as the span's **output** rather than silently dropped.

## Capability matrix

What each attachment point can actually do. Every ✅ is covered by a test in the package's
`tests/`.

| | observe | `before` hold | `error` hold | `after` hold | `inject` | `retry` | `abort` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `@gm.tool` / `gm.wrap_tools` (sync + async) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `gm.span` (sync + async) | ✅ | ✅ | — | — | as span output | — | ✅ |
| OpenAI `chat.completions` / `responses` | ✅ | ✅ | ✅ | ✅ | ✅ typed | ✅ | ✅ |
| OpenAI `with_raw_response` / `with_streaming_response` | ✅ | ✅ | ✅ | ✅ | ✅ typed, via `.parse()` | ✅ | ✅ |
| …the same with `stream=True` | ✅ | ✅ | ✅ | — | ❌ | ✅ | ✅ |
| Anthropic `messages.create` / `beta.messages.create` | ✅ | ✅ | ✅ | ✅ | ✅ typed | ✅ | ✅ |
| Anthropic `messages.stream` / `beta.messages.stream` | ✅ | ✅ (in `__enter__`) | ❌ | — | ❌ | ❌ | ✅ |
| LangChain sync handler | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ | ✅ |
| LangChain async handler | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ | ✅ |

Same shape as the [LangGraph JS matrix](/integrations/langgraph/#capability-matrix), and for the
same reason: a callback observes, a wrapper owns the call site. **Typed** means the injected value
comes back as the SDK type the call returns (`ChatCompletion`, `Response`, `Message`, ...), so a
framework that reads `.output`, `.usage` or `.content`, or checks `isinstance`, keeps working.

## The surface

| Call | What it does |
| --- | --- |
| `graphmind.init(app=...)` — alias `configure` | Create (or replace) the process-wide instance. |
| `graphmind.instrument_openai(client)` — alias `wrap_openai` | Gate every OpenAI request; returns the client. |
| `graphmind.instrument_anthropic(client)` — alias `wrap_anthropic` | Gate every Anthropic request; returns the client. |
| `gm.callback_handler()` — alias `gm.handler` | `BaseCallbackHandler` for sync chains. |
| `gm.async_callback_handler()` — alias `gm.async_handler` | `AsyncCallbackHandler` for async chains / LangGraph. |
| `@gm.tool` | Gate a function: a `tool:<name>` node with inject / retry / abort. |
| `gm.wrap_tools({...})` | The same, for a mapping, a list, or one callable. |
| `with gm.run("name"):` | Open a run. `async with` works on the same object. |
| `with gm.span("name", kind=...):` | A gated node for anything else. `async with` too. |
| `gm.ready(timeout=2.0)` / `await gm.ready_async(timeout=2.0)` | Wait for the handshake. `False` means detached, not an error. |
| `gm.stats()` | Diagnostics: enabled, attached, buffered, dropped, held gates, seq. |
| `gm.dispose()` | Release held gates, flush events, close the socket. Idempotent, no arguments. |

Every call above also exists as a method on an explicit instance (`graphmind.GraphMind(app=...)`),
which is what you want when one process debugs more than one agent.

<Aside type="note" title="async">
Sync and async are both first-class, and nothing here requires an event loop. `async def` tools
work with the same `@gm.tool` decorator; `async with gm.run(...)` and `async with gm.span(...)`
open a run or span in an async context; `await gm.ready_async()` is the async twin of
`gm.ready()`.

The transport lives on one dedicated daemon thread with its own event loop, so **your** loop is
never touched — no `nest_asyncio`, no `run_until_complete`, no hijacking. Run scoping uses
`contextvars`, which propagates to `asyncio` tasks (so concurrent tasks stay correctly
attributed) but **not** across a bare `ThreadPoolExecutor.submit` — use
`contextvars.copy_context().run(...)`, or open a `gm.run(...)` inside the worker.
</Aside>

## Naming nodes

One node per *code location*; executions light it up. The node name is the callable's
`__name__` — and for the two common callables that have none, GraphMind falls back to something
stable rather than a `repr` with a memory address in it:

```python
from functools import partial

load_eu = gm.tool(partial(load_region, "eu"))                 # -> tool:load_region
load_us = gm.tool(partial(load_region, "us"), name="load_us") # -> tool:load_us
```

A `functools.partial` is named after the function it wraps; an instance of a class with
`__call__` is named after its class. Two partials of the same function are therefore *one* node,
which is usually what you want — pass `name=` (or a key in `gm.wrap_tools({...})`) when you want
them apart.

## Same guarantees

The Python package holds the identical contract:

- **Never raises into your app.** Internal failures degrade to a rate-limited warning on stderr
  and uninstrumented behaviour. Your own exceptions propagate untouched.
- **Cheap when detached.** `tests/test_overhead.py` holds the budgets: under 20 µs per wrapped
  call when disabled, under 1 ms per wrapped call when enabled but detached (two envelopes into
  the replay ring buffer), and under 20 µs per detached gate check.
- **Fails open.** A debugger that disconnects mid-hold releases every gate with `continue` in
  well under 100 ms. An `atexit` hook does the same at interpreter exit, and the transport thread
  is a daemon, so GraphMind can never keep a process alive.
- **Bounded memory and payloads.** Events emitted while detached go into a ring buffer (default
  2,000 events, `buffer_size`) and are replayed with their original `seq` when a viewer attaches. Tool arguments and
  results are depth-, width- and length-capped before serialization; an LLM step's prompt is
  recorded in full (since 0.6), bounded only by the 512 KB per-event budget.
- **`fork()`-safe.** The loop thread is re-created in the child, so pre-forking servers
  (gunicorn, uvicorn workers, Celery) keep working.
- **Off in production.** See below.
- **Local-first.** Events go to `ws://127.0.0.1:4747/ingest` and no further.

## Durations and held time

Nodes are timed with `time.perf_counter()`, a monotonic high-resolution clock. `durationMs` is
fractional to 0.01 ms, so a 60 µs tool shows `<0.1ms` rather than `0ms`. `durationMs` is still
wall-clock time and includes any time a gate held the node. `node.finished` also carries
`heldMs`: the time the debugger held that execution, including holds on anything inside it. The
viewer shows ran time (`durationMs - heldMs`); see [durations](/reference/viewer/#durations).

Checked against a real server:

```text
node.finished tool:search    durationMs=0.6   heldMs=0
node.finished tool:search    durationMs=0.05  heldMs=0
node.finished agent:py-docs  durationMs=0.78  heldMs=0
```

For tests, `graphmind.clock.set_clock(fn)` substitutes the duration clock (a function returning
milliseconds), and `Session(clock=...)` drives only the held-time accounting.

## Recording less

The same four switches as the TypeScript client, with the same placeholder and the same wire
output: `GRAPHMIND_HIDE_INPUTS`, `GRAPHMIND_HIDE_OUTPUTS`, `GRAPHMIND_HIDE_TOOL_ARGS`,
`GRAPHMIND_HIDE_TOOL_RESULTS` (any value but `0`, `false`, `off`, `no` or empty turns one on), or as options:

```python
gm = graphmind.init(app="support-agent", hide_tool_args=True, hide_tool_results=True)
```

Either the environment or the option turning a switch on turns it on; `hide_inputs=False` cannot
undo `GRAPHMIND_HIDE_INPUTS=1`. Options also accept `1`, `"1"` and `"true"`. The hidden value
becomes `"__REDACTED__"` before the event is buffered, so a debugger that attaches later never
sees it. This covers `@gm.tool`, spans, the OpenAI and Anthropic instrumentation (streamed tokens
included) and the LangChain handlers. Checked with `GRAPHMIND_HIDE_TOOL_ARGS=1` against a real
server:

```text
node.started tool:search  input="__REDACTED__"  redaction={"count":1,"keys":["input"]}
```

Exception messages and tracebacks (`node.error`) are never redacted. The tool-only switches do
not hide the same data inside LLM messages; use `hide_inputs` and `hide_outputs` for that. The
full rules are on [environment → recording less](/reference/environment/#recording-less).
Conformance with the TypeScript client is tested, not assumed: `tests/test_redaction.py`
reproduces the shared fixture byte for byte and matches a differential file generated from the
TypeScript build.

## Loop hold

While a debugger is attached, the third call in a row of one tool with identical arguments, with
no other tool call between, is held before it runs, with reason `loop`. **Continue** runs it, and the next identical call is
held again. **Inject** substitutes a result; through a LangChain callback it degrades to
continue, as at any callback gate. **Abort** raises `GraphMindAbortError`. A retry does not
hold twice. With no debugger attached nothing is held and one line is logged per streak:

```text
[graphmind] possible loop: search (tool:search) was called 3× in a row with identical arguments; no debugger is attached to hold it (start `npx graphmind-ai` to pause it there). Polling on purpose? add it to loop_guard={'allow_nodes': [...]} or GRAPHMIND_LOOP_ALLOW; GRAPHMIND_ON_LOOP=off silences this
```

```python
gm = graphmind.init(
    app="support-agent",
    loop_guard={"threshold": 5, "allow_nodes": ["poll_job"]},  # or loop_guard=False
)
```

`loop_guard` takes `threshold`, `mode` (`"pause"`, `"warn"`, `"off"`), `allow_nodes`,
`ignore_keys` and `kinds`; camelCase keys are accepted too. For each field the option wins
over `GRAPHMIND_LOOP_THRESHOLD` / `GRAPHMIND_ON_LOOP` / `GRAPHMIND_LOOP_ALLOW`, which win over
the default. Python-specific comparison rules: Pydantic models compare by `model_dump()`, sets
ignore order, bytes are compared exactly, other objects compare by `repr()`, and an argument
that raises while being read is never counted as a repeat. Under `hide_inputs`, or
`hide_tool_args` on a tool, the loop's fingerprint is sent as `"__REDACTED__"`.

Fingerprinting runs on every watched tool call, attached or not; the test bounds it at 0.5 ms
for a 1 KB argument (`test_fingerprinting_a_1kb_input_is_cheap`), and it grows with argument
size. In a server that does not wrap each request in `gm.run`, every request shares one implicit
run, so the same call three times back-to-back across three separate requests counts as a loop.
Wrap requests in runs, or use `allow_nodes`. The general rules are on
[environment → loop hold](/reference/environment/#loop-hold).

## Environment

| Variable | Meaning |
| --- | --- |
| `GRAPHMIND_URL` | Ingest endpoint (default `ws://127.0.0.1:4747/ingest`) |
| `GRAPHMIND_DISABLED` | `1` (or any value but `0`, `false`, `off`, `no`) disables instrumentation — beats an explicit `enabled=True` in code |
| `GRAPHMIND` | `1` re-enables it in a production-looking environment |
| `GRAPHMIND_HIDE_INPUTS` / `_OUTPUTS` / `_TOOL_ARGS` / `_TOOL_RESULTS` | any value but `0`, `false`, `off`, `no`: [record less](#recording-less) |
| `GRAPHMIND_LOOP_THRESHOLD` / `GRAPHMIND_ON_LOOP` / `GRAPHMIND_LOOP_ALLOW` | The [loop hold](#loop-hold) |

"Production-looking" is a deliberately boring, documented rule rather than a heuristic: the
**first** variable that is set out of `GRAPHMIND_ENV`, `ENVIRONMENT`, `APP_ENV`, `PYTHON_ENV`,
`ENV`, `DJANGO_ENV`, `FLASK_ENV`, `NODE_ENV` decides, and it counts as production when its value
is `production` or `prod` (case-insensitive). No hostname sniffing, no cloud metadata probes.

A disabled session never opens a socket, never allocates a buffer and never touches your objects:
`instrument_openai` returns the client untouched.

## Known limits

<Aside type="caution">
- **`inject` / `retry` are unavailable at observer-only attachment points** — LangChain callbacks
  and Anthropic's `messages.stream`. Wrap the call site to get them.
- **`inject` cannot produce a stream.** On a plain `stream=True` call your payload is handed back
  as-is (code that iterates it gets no chunks); on a `with_raw_response` /
  `with_streaming_response` call with `stream=True` — the OpenAI Agents SDK's `Runner.run_streamed`
  — it is treated as `continue`. Both warn once. Inject on a non-streamed call.
- **A raw-response stream is observed through `.parse()`.** Read the body as bytes or lines
  instead (`iter_bytes()`, `iter_lines()`) and the node still starts, holds and finishes, but
  carries no text or usage.
- **No mid-stream gates.** A streamed response is observed, not pausable, once it has started.
  The gate is at the start of the call, matching the TypeScript adapters.
- **No provider-side timeout neutralization yet.** The TypeScript adapters neutralize SDK
  `timeout` configs while a debugger is attached; the Python SDKs' timeouts are still live, so a
  long hold can trip a client-side timeout after the gate releases. Remove aggressive `timeout=`
  settings while debugging.
- **Streaming usage needs the provider to send it.** For OpenAI chat streams, pass
  `stream_options={"include_usage": True}` or the node shows no token counts.
- **LangChain child-config propagation is LangChain's.** A manual `.ainvoke()` made *inside* an
  async lambda body inherits no run config, so that child produces no callbacks — for any
  handler, not just this one. Compose with `|` or pass `config=` explicitly.
- **CrewAI / LlamaIndex** are not instrumented directly yet. Both run on top of provider clients,
  so `instrument_openai` / `instrument_anthropic` plus `gm.span` already give you a usable graph.
- **A `GeneratorExit` traceback at loop shutdown is not ours.** `openai>=3` ships `httpcore2`,
  whose connection-pool async generator makes `asyncio` print
  `RuntimeError: generator didn't stop after athrow()` on the way out of `asyncio.run`. It
  reproduces on a bare `AsyncOpenAI` stream with GraphMind absent. Give the pool a real tick to
  finalize — `await client.close()` then `await asyncio.sleep(0.05)` — and it goes away
  (`asyncio.sleep(0)` is not enough).
</Aside>
