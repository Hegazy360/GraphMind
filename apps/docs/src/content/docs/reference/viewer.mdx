The viewer is the bundled UI the CLI serves at `http://127.0.0.1:4747`. This page is the map: if
you learn one thing from it, learn <kbd>⌘</kbd><kbd>K</kbd>.

## One header, one section

The viewer is a stack of places with exactly one on screen at a time:

```text
runs  →  run  →  node
```

The **breadcrumb in the header is the navigation** — `Runs › trip-planner › currencyConvert`,
every ancestor a link. <kbd>Esc</kbd> steps up one, and so does the browser's back button,
because each place is a hash URL.

**Connect an agent** and **Build a workflow** are side trips rather than steps: you take one
from wherever you are and come back. They extend the trail instead of replacing it — `Runs ›
trip-planner › currencyConvert › Connect an agent` — so every ancestor stays a link and
<kbd>Esc</kbd> returns you to the exact call you left. Both are in the menu under the
GraphMind mark, from any place.

That is the whole frame: a 46px header, and the place under it. There is no run rail, no
toolbar, no debug bar and no docked inspector — a seven-node run gets the window, a
three-hundred-node one gets all of it, and a stack trace is read across a reading column
instead of down a 392px gutter.

| Place | What it is for |
| --- | --- |
| **Runs** | Which run? A card per run with how it ended, how big, how long, what it cost, and the error it stopped on |
| **Run** | What happened? The summary line and the graph (or the waterfall), edge to edge |
| **Node** | One call. The decision if it is held, then why it failed, the payloads, the timings |

A run that is **held** gets a band directly under the header, on every place, naming the call
and why — a stopped process outranks wherever you happen to be standing. It never moves you:
seeing *where* in the shape a run stopped is most of the value of stopping it, so the graph
stays and the band offers the way in. <kbd>C</kbd>, <kbd>S</kbd> and <kbd>R</kbd> release the
hold from the graph without navigating at all; <kbd>I</kbd> and <kbd>E</kbd> step into the call,
because injecting and editing need the payload on screen.

## The command palette

<kbd>⌘</kbd><kbd>K</kbd> (or <kbd>Ctrl</kbd><kbd>K</kbd>) opens a palette over everything. It is
the fastest route to any node, any run, and every action on this page — so you never have to hunt
for a control.

| Type | To get |
| --- | --- |
| anything | Fuzzy search across the run's nodes and your recent runs |
| `>` | Actions only (or press <kbd>&gt;</kbd> to open straight into command mode) |
| `/` | Opens the palette from anywhere |

Arrow keys move, <kbd>Enter</kbd> runs, <kbd>Esc</kbd> closes. Selecting a node centres it on the
canvas and opens the inspector on it.

## Keyboard shortcuts

Shortcuts are ignored while you are typing in a field — except <kbd>⌘</kbd><kbd>K</kbd>, which
always works.

| Key | Action |
| --- | --- |
| <kbd>⌘</kbd><kbd>K</kbd> | Toggle the command palette |
| <kbd>/</kbd> | Open the palette (search) |
| <kbd>&gt;</kbd> | Open the palette (actions) |
| <kbd>Esc</kbd> | Close the palette, or deselect the current node |
| <kbd>F</kbd> | Follow the active node with the camera |
| <kbd>⇧</kbd><kbd>F</kbd> | Fit the graph to the screen |
| <kbd>⇧</kbd><kbd>A</kbd> | Re-arrange the layout (a full tidy-tree pass) |
| <kbd>⇧</kbd><kbd>T</kbd> | Toggle the timeline |
| <kbd>⇧</kbd><kbd>E</kbd> | Show only the error path |
| <kbd>⇧</kbd><kbd>C</kbd> | Collapse / expand all groups |
| <kbd>⇧</kbd><kbd>L</kbd> | Copy a deep link to this view |
| <kbd>Esc</kbd> | Step up one place (node → run → runs) |
| <kbd>[</kbd> / <kbd>]</kbd> | On a call: the previous / next call in execution order |
| <kbd>D</kbd> | Cycle the theme (system → dark → light) |

The toolbar's **View** menu holds the same three: which panes are open, how much of the graph
is folded, and the theme. The button carries the folded count, so a graph that is hiding part
of itself says so without being opened.

### While a gate is held

When execution stops at a gate, focus moves to **Continue** so the keyboard is already
where you need it, and four single-key shortcuts release the hold:

| Key | Action |
| --- | --- |
| <kbd>C</kbd> | Continue |
| <kbd>S</kbd> | Step |
| <kbd>R</kbd> | Retry |
| <kbd>I</kbd> | Inject — opens the editor; <kbd>⌘</kbd><kbd>Enter</kbd> sends it |

Abort has no shortcut on purpose: it ends the run, and a single keystroke is the wrong
amount of friction for that. Click it.

## The graph

One node per **logical** node, lit up per execution — see
[nodes and instances](/start/concepts/#nodes-and-instances). Nodes appear as the agent reaches
them, glow while running, and turn red on failure.

- **Follow** (<kbd>F</kbd>) keeps the camera on whatever is executing — the right default for
  watching a live run.
- **Fit** (<kbd>⇧</kbd><kbd>F</kbd>) zooms out to the whole graph.
- **Re-arrange** (<kbd>⇧</kbd><kbd>A</kbd>) runs a full layout pass. Live runs are laid out
  incrementally so nothing jumps under your cursor; after a long run this tidies the result.
- **Collapse** (<kbd>⇧</kbd><kbd>C</kbd>) folds sub-agents and chains into summary cards — the
  first thing to reach for on a graph you cannot take in at once. A run with more than 70 nodes
  opens folded on its own.

### Edges

Edges are right-angled lines routed through the gaps between cards, not curves drawn over them.
There is nothing to configure; this is the only edge style. An edge leaves the parent at the
middle of its bottom border, drops to a shared line halfway down the gap to the next layer, runs
sideways, and enters the child at the middle of its top border. When one step calls many things
at once, the children are packed into a grid; an edge to the second row or below travels down
the gutter to the left of its column and turns in just above its card. A fan-out therefore
reads as one trunk with drops.

What the test suite holds the layout to, on every change:

- **No edge passes through a card** other than the two it connects.
- **No two cards overlap.**
- **Every edge starts and ends on its cards' borders**, with a vertical first and last segment.

`apps/viewer/test/geometry.test.ts` checks these on eleven layouts: the demo and MCP runs, both
finished and held at a gate, fans of 5, 11 and 30 children, three nested levels, and the
300-node stress run folded and unfolded. `apps/viewer/e2e/geometry.spec.ts` checks the edges
the browser actually draws, sampled every 4px, against the real card boxes.

Dragging a card re-routes its edges as it moves. When a card pauses it grows to show its action
row; if that would push it into the row below, the grid is laid out again with the camera held
in place, so cards in that block can shift.

<Aside type="caution" title="What the routing does not cover">
Edges are routed for trees. A card you drag into another card's path is not routed around, and
an edge whose child sits above its parent is drawn as a straight line that may cross cards. The
runs GraphMind records do not produce such edges on their own.
</Aside>

### MCP protocol traffic is one folded card

A session recorded through [`graphmind mcp-proxy`](/integrations/mcp-proxy/) puts the calls you
care about (`tools/call`, `resources/read`, `prompts/get`, sampling, elicitation, completion)
directly under the session. Everything else goes under one node named **protocol**: the
handshake, the listings, `ping`, notifications, and any method GraphMind does not recognise. The
proxy asks the viewer to open that node folded, so a session first shows as a card like:

```text
protocol                                  GROUP
6 nodes      6 protocol calls      702ms
```

The count is how many calls are folded inside. The duration adds up the time those calls ran,
not counting time they were held. If any call failed, the card turns red and says how many.

- **Unfold** with the chevron on the card, or **Expand every group** (<kbd>⇧</kbd><kbd>C</kbd>).
  The fold is applied once, when the node first appears: after you unfold it, new events do
  not fold it again.
- **Gates still work inside the fold.** Every folded call is still a node. A breakpoint on
  `initialize` or `ping` still holds, and a failing handshake call still pauses on the default
  error breakpoint.
- A server that writes to stdout shows a red **stdout noise** node inside the fold. See
  [debugging MCP servers](/debugging/mcp-servers/#a-server-that-logs-to-stdout).

## Durations

A duration on a card, in the inspector, in the timeline or in the run list is **how long the
code ran**. Time the debugger spent holding it at a gate is not included.

| Where | What it shows |
| --- | --- |
| Card | Ran time. Once the node has been held, hover it for both numbers, e.g. `ran 19ms · held 161.2s`. |
| Inspector, this execution | **duration**, or separate **ran** and **held** cells once it has been held |
| Inspector, across executions | **total ran**, **avg** and **slowest**, plus **held** when anything was held |
| Timeline | Bar labels show ran time. The bar is drawn over the wall-clock span, with the held part hatched; the tooltip lists ran, held and wall. |
| Top bar | **wall** for the whole run, plus a **held** stat once any gate has held |
| Run list | Elapsed time minus held time. Hover it for both. |
| **Slow nodes** filter | Ranks by ran time, so a call you paused on is not flagged as slow |

Held time is counted for the node that was held **and for its parents**. If a tool is held for
40 seconds, its agent node also shows 40 seconds held.

Durations are printed with this rule:

| Value | Printed as |
| --- | --- |
| `0` | `<1ms`: under a millisecond, or measured by an older SDK whose clock only counted whole milliseconds |
| under 0.1 ms | `<0.1ms` |
| under 10 ms | one decimal, e.g. `2.4ms` |
| under 1 s | whole milliseconds, e.g. `312ms` |
| 1 s or more | seconds with one decimal, e.g. `38.1s` (minutes are also shown in seconds) |

The value is rounded before its format is chosen, so 9.96 ms prints as `10ms`, not `10.0ms`.
One exception: the timeline's hover card and the first-token cell in the inspector never switch
to seconds, so a 38-second step reads `38,142ms` there.

Where the numbers come from: SDKs from 0.5.0 time every node with a monotonic high-resolution
clock and send `heldMs` alongside `durationMs`. `durationMs` still means wall-clock time with
holds included, so recordings from older SDKs read the same as before. For those recordings the
viewer works out held time from the pause and resume events in the run. See
[`heldMs` in the wire protocol](/reference/wire-protocol/#events-app--viewer).

## When a loop is held

While a debugger is attached, the SDK holds the third call in a row of one tool with identical
arguments (the [loop hold](/reference/environment/#loop-hold)). The held card reads:

```text
Loop: 3× searchFlights with identical arguments
```

The usual action row sits underneath it. The inspector adds a block that shows:

- the arguments the agent keeps sending;
- each call in the streak with its output, tagged **same output as the call before** where it
  matches. When outputs are hidden by `GRAPHMIND_HIDE_OUTPUTS` they are never called the same;
- how to stop it holding a tool that polls on purpose: `loopGuard.allowNodes`, or
  `GRAPHMIND_LOOP_ALLOW=<tool>` (the only way under `graphmind mcp-proxy`), or
  `GRAPHMIND_ON_LOOP=warn`.

**Continue** runs that call, and the next identical call is held again. **Inject** hands the
model a different result, which is usually how the loop ends. **Abort** ends the run. In an
exported run the label reads `Was held — loop: …`. To see it without an agent, open
`?fixture=loop`.

## Hidden values

When the app runs with one of the `GRAPHMIND_HIDE_*` switches, the hidden input or output reaches
the viewer as the string `"__REDACTED__"`. The inspector shows a chip in its place instead of a
JSON viewer:

| Node | Input chip | Output chip |
| --- | --- | --- |
| Tool | `hidden by GRAPHMIND_HIDE_TOOL_ARGS or GRAPHMIND_HIDE_INPUTS` | `hidden by GRAPHMIND_HIDE_TOOL_RESULTS or GRAPHMIND_HIDE_OUTPUTS` |
| Any other kind | `hidden by GRAPHMIND_HIDE_INPUTS` | `hidden by GRAPHMIND_HIDE_OUTPUTS` |

A tool chip names two switches because either one produces the same event.

The inject editor is pre-filled with the execution's recorded output, or its input when there
is no output yet. If that value was hidden, the editor therefore holds the placeholder. If you
press **Inject & resume** without replacing it, the viewer refuses, keeps the editor open and
says:

```text
this value contains redacted content; edit it before injecting
```

The placeholder is refused anywhere in the value: as the whole value, inside a string, or as a
key. The server applies the same check, so a script or an older viewer cannot send the
placeholder into your app either. See [environment → recording less](/reference/environment/#recording-less).

## Filters

From the palette, to cut a large run down to what you care about:

| Filter | Shows |
| --- | --- |
| **Errored nodes** | Only nodes that failed |
| **Slow nodes** | p90 ran time and above, *for this run* (never below 200 ms; held time does not count) |
| **Paused nodes** | Only nodes currently held at a gate |
| **Error path** (<kbd>⇧</kbd><kbd>E</kbd>) | Dims everything that is not an ancestor of a failure |

Error path is the one to know: on a 200-node run it answers "what actually led here" in a
keystroke, instead of you tracing edges by hand.

Filters also narrow by node kind, and **Clear all filters** puts the whole graph back.

## The timeline

<kbd>⇧</kbd><kbd>T</kbd> opens a waterfall under the graph. It answers the questions the graph
cannot:

- what **overlapped** — which tool calls actually ran in parallel;
- where the **wall clock** went — the step that took eleven seconds is the widest bar;
- how long a step **waited before its first token**;
- when a **gate held**, and for how long: the held part of a bar is hatched, and its label shows
  only the time the code ran.

Rows are virtualised, so a thousand bars cost the same as thirty. Zoom with
<kbd>⌘</kbd>-scroll, the +/−/fit buttons, or by dragging a range on the ruler. Labels stay pinned
while you scroll horizontally. **Timeline only** hides the graph when you want the full height.

## The inspector

Click any node to open it: input, output, error with stack, duration, token usage, status, and
every instance of that node newest-first. See [inspecting a run](/debugging/inspecting/).

## How much is on screen

The run page ships as **Essentials**: the graph, the four figures in the top
bar, and an inspector that answers what happened, what went in, what came out
and how long it took. Five more panels exist and start switched off, because a
panel you have not needed yet is indistinguishable from clutter.

Open the chooser from the **View** menu, from the line at the bottom of a
call, or with <kbd>⌘</kbd><kbd>K</kbd> → "Customize the run page".

| Panel | Base | What it adds |
| --- | --- | --- |
| Why it failed | ✅ | The error, its stack, the input that caused it, the siblings that did not fail |
| Input and output | ✅ | The values this call received and returned |
| Timing and tokens | ✅ | Duration, held time, token counts for this one execution |
| Minimap and size readout | ✅ | Only ever drawn on a graph big enough to need them |
| Context and cost | — | What the model saw, how it changed since the previous step, the estimate |
| History | — | Totals across every execution of this node, and who released its holds |
| Streamed text | — | The tokens as they arrived, plus any reasoning trace |
| Node id | — | The logical id and a deep link to this exact node |
| Connection detail | — | Who this tab is to the server, what a coding agent may do, the endpoint |

**Essentials** and **Everything** are shortcuts, not modes: change any single
toggle and you are in `custom`, with nothing lost and nothing to undo. The
choice is stored in the browser and applies to every run.

<Aside type="caution" title="What a preset can never hide">
Why a run is held, and the row that releases it. The pause banner, the hold
evidence (loop streaks, repeated errors, error-shaped results) and
Continue / Step / Retry / Inject / Edit / Abort are not panels — a debugger
that could be configured into not telling you it had stopped would be worse
than no debugger.
</Aside>

## The header

The breadcrumb, whether anything is attached, and three menus.

The connection light never flatters the connection: an open socket is not a live tail, so a
server still replaying history says `catching up 12,048/72,144` and a stream that has fallen
behind says `behind 34s`.

- **Debug** — Run / Step, **Break everywhere**, and a removable chip for every armed
  breakpoint, including the default pause-on-error one. Session state, not per-run, so it
  lives behind a menu; the button carries the armed count and reads `Step` when stepping. See
  [breakpoints & step mode](/debugging/breakpoints-and-step/). In a run exported by
  `graphmind record --html`, or in a tab without the viewer token, these are disabled and say
  why. The endpoint and the control chip are the **Connection detail** panel, off in the base.
- **View** — how much detail, which panes, how much is folded, the theme.
- **Search** — the palette.

## The run summary

One line above the graph: the status, then the four figures you want before you look at it —
**nodes**, **errors** (only when there are any), **wall** time and the **est. cost**.
Everything else the run reported — llm steps, tool calls, running vs held time, the token
breakdown with cache reads and writes — is under **Totals**, whole, and never truncated to
fit. **Filter** dims what it excludes rather than hiding it.

## Deep links

The viewer's routes are plain hash URLs:

```text
http://127.0.0.1:4747/#/runs
http://127.0.0.1:4747/#/run/<runId>
http://127.0.0.1:4747/#/run/<runId>/node/<nodeId>
http://127.0.0.1:4747/#/build
http://127.0.0.1:4747/#/connect
```

These are the places, so the browser's history is the stack: going back from a call lands on
its run, and back again on the list.

Both segments are URI-component encoded, so `tool:issueRefund` appears as `tool%3AissueRefund`.

<kbd>⇧</kbd><kbd>L</kbd> copies a link to the current view — paste it into an issue, a message,
or your notes and it reopens exactly there. The [MCP tools](/reference/mcp/) return these same
links, so a coding agent can cite the precise node it is talking about.

<Aside type="note" title="Two viewers, one server">
Breakpoints and mode live on the server, not in a browser tab. Two windows on the same server
see the same debug state, and a change in one broadcasts to the other — which is what makes
"open the good run and the bad run side by side" work. See
[comparing runs](/debugging/comparing-runs/).
</Aside>

## Connect an agent

`#/connect`, the header menu, or "Connect an agent" in the palette. A viewer that opens with
nothing attached and no runs lands here on its own, once.

One screen: pick the SDK your agent already uses, and copy the install command and the two
lines it needs. The page also states what a gate can actually do for that stack *before* you
wire it up — LangChain callbacks can hold a node but not change what it returns — and whether
anything is currently listening, in the same dot-and-label the header carries. Your choice of
stack is remembered.

There is deliberately no wizard here. It was five steps, and four of them were ceremony: a
menu in front of a menu, a Next button between two code blocks that belong together, and a
step whose content was "now run your app, and leave this tab open" — which is what the rest
of the viewer is for.

## The Build page

`#/build`, the **Build a workflow** button in the run list, or "Build a workflow" in the
palette. Describe one agent and its tools, pick the language and SDK, read the instrumented
project the server generates, write it to disk with your key in a private `.env`, and run it
from the page; the run appears in the list beside the log. It needs the viewer token, and the
page says so when a tab has none. The whole flow, and where its boundaries are, is on
[build a workflow](/guides/build-a-workflow/).

## Built-in fixtures

The viewer can render these runs with no server, no agent and no API key. They are useful for
seeing what a shape looks like before you instrument anything, and for reporting a UI bug
against something everyone has:

```text
http://127.0.0.1:4747/?fixture=demo   the planted-bug trip planner
http://127.0.0.1:4747/?fixture=mcp    an MCP session, with the protocol calls folded
http://127.0.0.1:4747/?fixture=loop   an agent held on its third identical searchFlights call
http://127.0.0.1:4747/?stress=300     a generated 300-node graph, for layout and performance
```

`?stress=<n>` accepts 8–4000 nodes and takes optional `&events=<n>` and `&pace=<ms>`.

The empty state offers the demo, the MCP session and the stress run as buttons, so you do not
have to remember the query parameter. A fixture is clearly badged as recorded — it is not a live run and nothing in
it can be resumed.

## Imported and replayed runs

A run brought in by `graphmind import` is rendered with the viewer's "imported" treatment:
history only. Nothing is executing, so there is nothing to pause, and the control affordances are
not offered. `graphmind demo` replays a recording through the real pipeline, so it *does* pause
for real.
