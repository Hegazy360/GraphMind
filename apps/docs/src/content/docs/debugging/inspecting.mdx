Click any node to open the inspector. It shows what that node actually received and produced —
not a rendered summary, the values themselves.

## What a node shows

| Field | Detail |
| --- | --- |
| **Input** | Tool arguments, or the messages and settings going into a model step. A value hidden by a `GRAPHMIND_HIDE_*` switch shows as a "hidden by …" chip. |
| **Output** | The return value, or the model's completion |
| **Error** | `name`, `message` and `stack` when the node threw |
| **Duration** | How long the code ran. Once a gate has held the execution, the inspector splits it into **ran** and **held**; see [durations](/reference/viewer/#durations). |
| **Usage** | `inputTokens` / `outputTokens` on LLM nodes, plus cache read / cache write / reasoning when the provider reported them (see [usage and cost](#usage-and-cost)) |
| **Status** | `ok`, `error` or `aborted` |
| **Instances** | Every execution of this logical node, newest first |

Inputs and outputs render as an expandable JSON tree, so a large tool result stays navigable
instead of becoming a wall of text.

## Instances: the same node, many executions

One node on the canvas can hold many executions. A retrieval tool called eleven times is **one**
node with eleven instances — select an instance to see that call's own input, output, duration
and usage.

This is the payoff of stable node ids. You are looking at one place in your code and its
history, which is almost always the question you actually have ("what did `searchOrders` get
called with, across this run?").

<Aside type="note" title="Concurrency">
Each execution carries an `instanceId`, so results are attributed to the right call even when
the same node runs several times in parallel. Without it a receiver would have to guess by
recency — which is wrong exactly when it matters.
</Aside>

## Streamed tokens

Model nodes accumulate their stream live. Deltas arrive batched (roughly 30 per second per node,
so the UI stays smooth on a fast provider) on three channels:

| Channel | Contents |
| --- | --- |
| `text` | The visible completion |
| `reasoning` | Reasoning / extended-thinking output where the provider exposes it |
| `tool-args` | Tool arguments as the model streams them |

Watching `tool-args` stream is often the fastest way to see a model committing to a bad call —
you can have a breakpoint on that tool waiting before it finishes writing the arguments.

## Usage and cost

`node.finished` on an LLM node carries `TokenUsage`. The viewer shows it per step and rolled up
for the run, which makes the "why did this run cost eleven cents" question answerable in one
look: usually one tool returning a huge blob that gets re-sent on every subsequent step.

Since 0.6 every SDK (TypeScript, Python, Ruby) writes usage the same way:

| Field | Meaning |
| --- | --- |
| `inputTokens` | The **whole prompt**, cached tokens included — tokens read from the provider's cache and tokens written to it are part of it |
| `outputTokens` | The completion, reasoning tokens included |
| `inclusive` | `true`: `inputTokens` is that total. Stamped on every usage a 0.6 SDK writes |
| `cacheReadTokens` | Prompt tokens served from the provider's cache |
| `cacheWriteTokens` | Prompt tokens written to the provider's cache (Anthropic's 5-minute and 1-hour writes, summed) |
| `reasoningTokens` | Output tokens spent reasoning |

The last three appear **only when the provider reported them** — a reported `0` stays `0`, an
unreported count is absent, never filled with `0`. Providers disagree about what "input" means
(Anthropic's `input_tokens` is only the uncached tail; OpenAI's `prompt_tokens` already includes
cached tokens; ruby_llm counts input without cache), so each adapter adds the cache counts back
where its provider left them out. That is what makes one step comparable with the next.

Events recorded before 0.6 carry no `inclusive` marker. The viewer and `graphmind mcp` show
their `inputTokens` **as reported** (it may exclude cached tokens), labelled so. The one
exception is the 0.5 Anthropic TypeScript adapter, recognisable by `cacheCreationTokens`: its
total is recomputed from the uncached count plus the cache fields.

The older field names stay as aliases through 0.6.x: `cacheCreationTokens` (Anthropic
TypeScript) equals `cacheWriteTokens`, and `cachedInputTokens` (OpenAI TypeScript) equals
`cacheReadTokens`; the OpenAI adapter also keeps `totalTokens` as reported.

**Cost** is priced per step and per model from a bundled snapshot of
[genai-prices](https://github.com/pydantic/genai-prices) (MIT; the notice ships with the viewer as
`THIRD_PARTY_NOTICES.txt`): the uncached share of the prompt at the input rate, cache reads and
cache writes at their own rates, output at the output rate. Every figure is labelled
**≈ est. (prices as of 2026-09-22)** — it answers "which step is eating the budget", never a
bill. A model the snapshot does not know gets **no dollar figure** rather than a guess, and a
run's total counts only the steps it could price (the tooltip says how many it left out). The
price table is a separate download the viewer fetches only for a run with token usage; a
single-file export (`graphmind record --html`) opened from disk shows no cost.

## Context & cost: what changed since the previous step

Selecting an LLM step opens **Context & cost** at the top of the inspector: the usage above, how
full the model's context window was, the step's cost and the run's cost so far — then the prompt
compared with the **previous LLM step of the same agent**:

- the first message that differs, and the messages added, removed ("trimmed?") or changed — open
  any of them to read it, or to see a changed one as a line diff;
- the system prompt, as a line diff;
- tools added, removed or changed — by the schema hash every 0.6 SDK records, so a tool whose
  definition changed under the same name opens as a diff of its two definitions;
- sampling parameters (`temperature`, `max_tokens`, `tool_choice`, …) and the model, when they
  changed;
- where a provider's prompt cache stops matching: caches are prefix-based over tools, then the
  system prompt, then the messages, so the first changed part is where the step starts paying the
  full input price. Moving a cache breakpoint (`cache_control`) is not a change.

When more than five minutes passed between the previous step and this call, the view says so —
**"Held 8 min before this call — the provider's 5-minute prompt cache has likely expired"** when
a debugger hold accounts for the gap, so a cache-write spike after a long pause is not a mystery.

The comparison **refuses, and says why**, when either side is not the prompt that was sent: the
event was shrunk to the 512 KB limit, a value in the prompt was redacted (`GRAPHMIND_HIDE_INPUTS`
or a secret-shaped key — two hidden values cannot be compared), the input is a preview, several
prompts went out in one batched call, or an OpenAI Responses call continued a server-side
conversation (`previous_response_id`) and sent only the new items.

## Live vs. history

The inspector works the same on a finished run. Pick any run from the run picker and read it
node by node; the whole event stream is persisted in SQLite. The only difference is that a
finished run has nothing to resume.

If you attach *mid-run*, the client replays its ring buffer (5,000 events by default in TypeScript, 2,000 in Python and Ruby) oldest-first
with the original sequence numbers, so you get the history you missed and the viewer
deduplicates on `(runId, seq)`.

## Finding a node quickly

<kbd>⌘</kbd><kbd>K</kbd> opens the command palette: fuzzy-search every node in the run by name,
hit <kbd>Enter</kbd>, and the canvas centres it with the inspector open. The full UI map is on
[the viewer](/reference/viewer/) page; for the wider strategies — collapsing, filtering,
long-running runs — see [big & long-running graphs](/debugging/large-graphs/).

## Reading a run from your coding agent

Everything the inspector shows is also available over MCP, so Claude Code or Cursor can pull up
the failing run and reason about it with you:

```sh
claude mcp add graphmind -- npx graphmind-ai mcp
```

`list_runs`, `get_run`, `get_node` and `find_errors` read the SQLite database directly — they
work with the viewer closed. See the [MCP reference](/reference/mcp/).
