> Status: v1 · M0–M4 ✅ (tested by founder) · M5 ✅ built 2026-11-11 (awaiting founder test) · operator accounts ✅ built 2026-11-11 (`@graphmind-ai/accounts`, `jack serve --accounts`) · next M6 (hardening) · 2026-11-08 · service name **Jack** (GraphMind Jack)
> Proposed: Jack is a **separate service under the GraphMind brand, in this repo**, MIT like the

## 0. Positioning

**One line:** point us at the API you already have, and get a hosted, OAuth-protected MCP server
that any AI client can connect to. No MCP code to write and no spec churn to follow.

**The problem.** To be usable from Claude, ChatGPT, Cursor or VS Code, a company has to:
(1) write an MCP server, (2) host it on Streamable HTTP, (3) implement the MCP authorization
profile (Protected Resource Metadata, an OAuth 2.1 authorization server, PKCE, client
registration through CIMD and/or DCR, audience-bound tokens), (4) connect that to its existing
user accounts, and (5) keep all of it current as the spec revises (2025-03 → 2025-06 → 2025-11 →
2026-07 changed transport, auth and registration every time). Most of this work has nothing to
do with the company's product.

**What the engineer does (target: under 30 minutes, no new code in the happy path):**

1. `npx jack init`: finds or accepts an OpenAPI document (file, URL, or one generated by the
   framework) and produces `jack.yaml`, a reviewable file listing the generated tools.
2. Curates the tools in that file: picks endpoints, renames them, rewrites descriptions, groups
   them into toolsets. `jack preview` serves it locally so it can be tried in Claude Code first.
3. Chooses how users sign in (§3.4): their existing OAuth/OIDC provider, a single "link account"
   endpoint on their app, or per-user API keys.
4. `jack deploy` returns `https://acme.mcp.graphmind.ai/mcp` (or `mcp.acme.com`). They publish
   it, and their users add it to any MCP client and sign in.

**Pillars (priority order):**

| # | Pillar | Why |
|---|---|---|
| J1 | **Auth that matches the app's existing users.** We act as the MCP authorization server and federate to the app's own sign-in | This is the hardest part to build in-house, and where generators stop (§0.1) |
| J2 | **Generated, then curated, kept in git.** OpenAPI → tools, plus a reviewed overlay (`jack.yaml`) | Raw "one endpoint = one tool" conversion gives poor agent results (§0.1) |
| J3 | **We follow the spec.** Protocol revisions, transport fallback and client quirks are handled by us | This is the maintenance burden the user described |
| J4 | **Every call is recorded.** Per-tool call log, failures, latency, and which client/user called. GraphMind's debugger can attach | Uses what GraphMind already does |

**Non-goals for v1:** running customer code (no custom tool handlers, so there is nothing to
sandbox; that is v2 via Circuit runners), GraphQL/gRPC sources, MCP resources/prompts beyond
basics, a marketplace or directory.

**The gap, in one line:** today an engineer can generate tools from OpenAPI (Kong, APIM,
AgentCore, FastMCP), but connecting *their own users* to an MCP server that follows the spec is
still something they build themselves. Jack makes that the default.

### 1.1 Key design decisions

- **Declarative proxy, not generated code.** A deployment is an immutable *manifest* (JSON:
  tools, their input schemas, and the HTTP mapping for each one). The runtime interprets it.
  Nothing the customer writes ever executes on our side, so v1 needs no sandbox, and spec
  upgrades are a runtime change that every deployment picks up without redeploying.
- **Two token worlds, never mixed.** The MCP client only holds a Jack-issued token whose
  audience is the project's MCP URL. Upstream credentials (the app's OAuth tokens, a linked-user
  assertion, or an API key) stay encrypted in our store and are attached server-side. This is
  what the spec requires (no token passthrough), and it also lets a user revoke access in one
  place.
- **One host per project.** `<project>.mcp.graphmind.ai` (custom domain via CNAME + managed
  certificate). Per-project origin isolates the consent page's cookies and CSRF, and gives each
  project its own issuer and resource identifier, which is what MCP clients key on.
- **Control plane and data plane are separate Hono routers in one app**, built so they can be
  split into separate deployables when hosted (the data plane is the hot, internet-facing path).
- **Store interface with two backends**, as Circuit does: `node:sqlite` for dev and tests,
  Postgres for hosted. No Docker for local development.

## 3. Specs

### 3.1 Ingestion: "use the code and endpoints you already have"

Ordered by how much the engineer has to do:

1. **OpenAPI document (v1, primary).** File, URL, or the framework's live endpoint
   (`/openapi.json` for FastAPI, `/api-json` for NestJS, `/v3/api-docs` for Springdoc,
   rswag for Rails). `jack init` probes the common paths on a running local server.
2. **Framework extractors (v1.1).** For apps without a spec: a `jack scan` that asks the
   framework to emit one (Hono `@hono/zod-openapi`, Fastify swagger, Express with zod-to-openapi)
   or reads route tables. Output is always an OpenAPI document, so there is a single compiler.
3. **Postman collections / HAR capture (v1.2).** Converted to OpenAPI first, then the same path.
4. **Code annotations (v2).** `@mcpTool` decorators in TS/Python/Ruby that add descriptions
   and grouping to the spec. Not required for anything to work.

Tool generation rules (in `jack-openapi`):

- One tool per `operationId`, or per method+path when there is none. Names are snake_case,
  at most 64 characters, deduplicated.
- Input schema = merged path + query + header (non-auth) + body parameters, flattened into one
  object. Name collisions are prefixed (`path_id`, `body_id`). `$ref`s are inlined, recursion is
  cut at depth N, and `format`, `enum` and `description` are kept.
- Annotations: GET/HEAD → `readOnlyHint: true`. DELETE → `destructiveHint: true`.
  PUT → `idempotentHint: true`. All can be overridden in `jack.yaml`.
- Description = `summary` + `description`, trimmed. The lint flags empty or one-word
  descriptions, because they are the main reason models pick the wrong tool.
- **Default exposure is opt-in for writes.** `init` enables read operations and lists write
  operations as disabled, so publishing destructive tools is always a decision someone made.
- The lint warns above about 30 enabled tools and suggests toolsets.

`jack.yaml` (reviewed in a PR, compiled into the manifest at deploy):

```yaml
source: ./openapi.json            # or https://api.acme.com/openapi.json
upstream: https://api.acme.com    # the only host this project may call (§3.6)
auth: { mode: oidc, issuer: https://auth.acme.com, scopes: [openid, invoices:read] }
toolsets:
  billing: [list_invoices, get_invoice, refund_invoice]
tools:
  list_invoices:
    description: "List the signed-in user's invoices, newest first. Use get_invoice for line items."
    response: { pick: "$.data[*].{id,amount,status,created}", maxBytes: 20000 }
  refund_invoice:
    enabled: true
    annotations: { destructiveHint: true }
    requiredScopes: [invoices:write]   # step-up: 403 insufficient_scope → client re-authorizes
  delete_account: { enabled: false }
```

### 3.2 Runtime (tool call path)

1. `createMcpHandler` receives the request. `requireBearerAuth` verifies our JWT
   (signature, `aud` = this project's MCP URL, expiry, not revoked) → `AuthInfo{ grantId, sub, scopes }`.
2. `tools/list` returns the active deployment's tools, filtered to the scopes the grant has.
3. `tools/call`: check the arguments against the JSON schema → build the request from the
   mapping (path template, query, headers, body) → resolve the upstream credential for this
   grant (§3.4), refreshing it if it has expired → egress guard (§3.6) → `fetch` with a timeout
   (default 30 s) and a response-size cap.
4. Response shaping: JSON → `structuredContent` + a text summary. Optional `pick` projection.
   Truncate at `maxBytes` and say so explicitly in the result. Pass Link/cursor pagination
   through as a `next_cursor` field. Upstream 4xx → `isError: true` with the problem body (the
   model can recover). Upstream 401 → refresh once, then the error asks the user to reconnect.
5. Record the call: tool, grant, client id, status, latency, sizes. Arguments and results are
   **off by default** and can be enabled per project with redaction (`redact-secrets` approach).

Protocol support: 2026-07-28 only (`server/discover`, `_meta` versioning). The handler runs with
`legacy: 'reject'`: a 2025-era client gets the unsupported-version error naming the revision we speak. Responses are plain
JSON; SSE only for calls that report progress. Confirmation of destructive tools (opt-in per
tool) uses MRTR `input_required` rather than deprecated elicitation requests. Tasks extension: not
needed in v1 because proxied calls are short. Set `ttlMs` on `tools/list` so clients cache it.

### 3.3 Deployments

- Immutable and versioned: `deployments(id, project_id, version, manifest, manifest_hash, created_by)`.
  Promoting one is a pointer swap with instant rollback.
- **Diff on deploy**, reusing `toolHash` from `circuit-mcp/gateway.ts`: added, removed and changed
  tools are shown before promotion. A changed description or schema is flagged because clients
  that pin tools (Circuit among them) will notice.
- Preview deployments at `<project>--<version>.mcp.graphmind.ai` for testing.

### 3.4 Authentication (J1)

Two separate questions:
**(a) How the AI client gets a token for the MCP server.** This is always the same: Jack is
the MCP authorization server, per project.
**(b) Who the user is in the customer's app, and how Jack calls the API as that user.** The
customer picks one *auth mode*.

#### (a) MCP-facing authorization server (`jack-auth`), identical for every mode

- `/mcp` without a token → `401` + `WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource"`.
- PRM (RFC 9728): `resource` = canonical MCP URL, `authorization_servers` = [project issuer], `scopes_supported`.
- AS metadata (RFC 8414) at the issuer: `code_challenge_methods_supported: [S256]`,
  `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported: [none, private_key_jwt]`,
  `registration_endpoint` (DCR compat), `grant_types_supported: [authorization_code, refresh_token]`
  (+ `jwt-bearer` with the ID-JAG profile once EMA lands).
- **Clients:** CIMD (fetch `client_id` URL through the egress guard, HTTPS only, ≤ 5 KB, 3 s, cached
  per `Cache-Control`; `redirect_uris` matched exactly; loopback any port) → DCR fallback
  (rate-limited per IP/project, unused registrations GC'd after 30 days) → static clients the
  customer pre-registers.
- `/oauth/authorize` requires PKCE S256 and `resource` (RFC 8707) equal to this project's MCP URL;
  anything else is rejected.
- **Tokens:** access token = JWT (ES256, per-project key with `kid`, 15 min, `aud` = MCP URL,
  `sub`, `grant_id`, `scope`, `client_id`). Refresh tokens are opaque, stored as hashes, rotated on
  every use, and reuse revokes the whole family. A revocation check by `grant_id` happens on every
  call (cached a few seconds), so revoking a grant takes effect immediately.
- **Consent screen** (hosted, styled with the customer's logo and colours): shows the client's
  **domain** taken from the `client_id` URL, not only its self-declared name, plus the toolsets
  and scopes requested. Remembered per (subject, client_id, scopes). `frame-ancestors 'none'`,
  CSRF token, `state` bound to the session cookie on the project host.
- Step-up: a tool with `requiredScopes` the grant lacks → `403 insufficient_scope scope="..."`,
  and the client re-authorizes.

#### (b) Auth modes: connecting to the customer's users

| Mode | For apps that… | Customer effort | How the upstream call is authenticated |
|---|---|---|---|
| **`oidc`** (federation) | already have OAuth/OIDC (Auth0, Okta, Cognito, Clerk, Keycloak, Entra, own) | Register Jack as a confidential client (callback `https://<host>/oauth/upstream/callback`) and paste client id/secret | The user's **own upstream access token**, obtained in the same flow and refreshed by Jack |
| **`link`** (account linking) | use their own session login with no OAuth server | **One route plus one middleware** (`jack-verify`) | Project service credential + a short-lived **`Jack-Assertion`** JWT (signed by Jack, `aud` = upstream, `sub` = linked user, `scope`, 60 s) that the middleware verifies against the project's JWKS |
| **`apikey`** | issue per-user API keys | None | The key the user pasted on our consent page, checked against a configured `whoami` operation before storing |
| **`none`** | have public APIs | None | Optional fixed project key; the MCP endpoint can still require sign-in for rate limiting |

**`oidc` flow:** client → `/oauth/authorize` → Jack stores the pending request and redirects to
the customer's IdP with *its own* `state` and PKCE → IdP callback → Jack exchanges the code,
verifies the `id_token` (`iss`, `aud`, `nonce`), and sets subject = `iss|sub` → consent → Jack
issues its own authorization code to the MCP client → token endpoint. The upstream tokens are
encrypted with the grant and never sent to the client. This is the confused-deputy-safe proxy
pattern, because consent is per (subject, MCP client) even though Jack is one upstream client.

**`link` flow:** Jack redirects to `link_url?request=<JWT: jti, project, return, exp 5 m>` →
the customer's app, where the user is logged in through its normal session, calls
`jack.verifyLinkRequest()` and redirects back with `jackLink(userId, {scopes})`, which signs
the response with a key from the project's settings → Jack verifies it and the flow continues
to consent. This is the "low involvement" path: no OAuth server to stand up.

**Enterprise-Managed Authorization (v1.x):** accept ID-JAG jwt-bearer grants from the
customer's enterprise customers' IdPs (Okta first), so employees connect without a consent click.

### 3.5 Control plane API (v1)

```
POST   /v1/projects                         create (slug → host)
PUT    /v1/projects/:id/source              upload/point to OpenAPI; returns generated jack.yaml
POST   /v1/projects/:id/deployments         manifest from jack.yaml → validated, diffed
POST   /v1/projects/:id/deployments/:v/promote
PUT    /v1/projects/:id/auth                auth mode + IdP client credentials (stored encrypted)
POST   /v1/projects/:id/test-call           run a tool as a test user from the dashboard
GET    /v1/projects/:id/calls               call log (cursor-paginated)

POST   /v1/projects/:id/domains             custom domain + verification record
```

Auth: hashed API keys `jk_<env>_<random>` (as Circuit). Errors follow RFC 9457.

### 3.6 Security & tenancy

- **No token passthrough, ever.** The MCP access token never leaves Jack, and upstream
  credentials never reach the client, the call log or error messages. Add Jack to the
  `security/` canary audit: plant fake upstream tokens and API keys, then grep the DB, call log,
  API responses, dashboard and exports. **CI job from M0**, as Circuit did.
- **Egress guard (SSRF):** each project calls only its verified `upstream_base_url` host
  (ownership proven with a DNS TXT record or `/.well-known/jack-verification`). Path
  parameters are percent-encoded and may not contain `/`, `..` or `?`. DNS is resolved by us,
  with private, link-local, loopback and metadata ranges blocked (v4 and v6), and the resolved IP
  pinned for the connection (DNS-rebinding defence). No redirects followed off-host. The same
  guard covers CIMD and `jwks_url` fetches.
- **Tool poisoning from the spec:** strip invisible and bidi Unicode (including TAG characters
  U+E0000–E007F) from names and descriptions at compile time. Deploy diffs (§3.3) make every
  description change reviewable. Lint for instruction-like text in descriptions.
- **Prompt injection through outputs:** results are framed as data. Destructive tools carry
  `destructiveHint` and can require MRTR confirmation. Per-grant rate limits.
- **Tenancy:** tenant id on every row through a repository layer (Postgres RLS in hosted, as
  in Circuit §3.10). One host and issuer per project, and per-project signing keys, so a token
  from project A can never verify at project B (`aud` + `iss` + `kid`).
- **Secrets:** IdP client secrets and upstream tokens use envelope encryption. Signing keys
  rotate with a JWKS overlap window.
- **The customer's side:** `jack-verify` checks the assertion's signature, `aud`, `exp`
  (≤ 60 s) and `jti` replay protection, so a stolen assertion is useless within a minute.

## 5. Decisions (resolved 2026-11-08)

1. **Name: Jack.** Free in the repo; `relay` is taken by the debugger's MCP proxy.
2. **v1 auth modes: all four** (`oidc`, `link`, `apikey`, `none`). `link` is what
   delivers "low involvement" for apps without OAuth, and `apikey` costs almost nothing.
3. **No customer code in v1: agreed.** A declarative proxy only, so no sandbox is
   needed until custom tools arrive through Circuit runners.
4. **Protocol floor: 2026-07-28 only, legacy rejected.** No users today, so no legacy code to carry.
5. **License: MIT** for now, including the authorization server (Gram is AGPL; MIT helps self-hosting).
6. **Relationship to Circuit: separate.** Separate service that shares only schema helpers and
   `toolHash`. Integration (workflows as tools on a Jack endpoint) is a later milestone, not
   a dependency.
7. **Pricing (still open, not blocking):** per monthly active connected user versus per call. Competitors anchor
   on calls (Composio $0.0003/call, AgentCore ~$0.005/1k ⚠).

## 8. Surfaces: who uses a UI, who uses code (decided 2026-11-11: full dashboard in M4, iterate from there)

Two kinds of people touch Jack, and only one of them is an engineer:

| Who | What they do | Surface | Built |
|---|---|---|---|
| **End users** of the customer's app | Connect an AI client, sign in, approve | Jack's hosted sign-in, consent and approval pages; their AI client | ✅ M3 (no code, no setup) |
| **The customer's team** setting Jack up | Import the API, pick and describe tools, configure sign-in, test, deploy, watch usage | **Dashboard** (M4), with the CLI + `jack.yaml` as the equivalent for engineers who want config in git | CLI ✅ M1–M3 · dashboard M4 |

**Principle: one source of truth, two editors.** The dashboard and `jack.yaml`
edit the same project configuration. In the dashboard, a change is saved and
deployed in the browser, and "Export jack.yaml" gives an engineer the file. With
the CLI, `jack deploy` uploads a reviewed file. Git sync (connect a repo; the
dashboard opens pull requests instead of saving directly) is a later option for
teams that want review on every change, and is what n8n users complain is
missing.

**Why the CLI came first.** M0–M3 had to prove the hard, invisible parts:
spec → tools, the runtime, and spec-compliant OAuth. A UI on top of an
unproven engine just moves the bugs. Every M4 screen calls something that
already exists and is tested:

| Dashboard screen | Calls (already built) |
|---|---|
| Import | `loadSource` + `generateConfig` (M1) |
| Tools (toggle, rename, describe, confirm, scopes) | `compile` + lint codes J001–J013, live (M1) |
| Sign-in setup | `planAuth`/`resolveAuth`, plus "test sign-in" running the real flow (M3) |
| Try it | the runtime with the operator's own grant (M2/M3) |
| Deploy / rollback | `/v1` deployments, `diffManifests` (M0) |
| Users | `listGrants` / `revokeGrant` (M3) |
| Activity | `CallRecord` stream (M2) |

**Stack for the dashboard:** a dependency-free SPA served by `jack-api` with a
strict CSP, like Circuit's dashboard. No build step, and hosted can serve it
unchanged. Operator sign-in for the dashboard itself is part of M4. Local use
needs none, hosted uses session cookies, as Circuit §1.3 planned.

## 9. M3 notes

- **Fail-open bug found and fixed during M3.** `@hono/node-server` replaces the
  global `Response` class, so `result instanceof Response` was false for the
  SDK's own 401 response. The bearer gate then treated the 401 as a signed-in
  user. The fix is explicit control flow: `verifyBearerToken` throws on every
  failure, and nothing type-sniffs a result. `instanceof Response` is now
  banned in Jack code paths (none remain), and the unauthenticated-401 test
  guards it.
- **Behaviour change from M2.** `apikey` mode without `JACK_UPSTREAM_API_KEY`
  used to refuse to start. It now runs per-user sign-in. Setting the variable
  keeps single-user mode.
- **Short upstream tokens.** If the customer's IdP issues tokens that live
  under 60 s, Jack renews them on every call (renewals are single-flight per
  grant). That is correct but chatty, so the M4 dashboard should flag it.
- **Not yet:** `link` mode (M5), Enterprise-Managed Authorization (later),
  remembering consent per user and client (every sign-in asks; the safe
  default), and OAuth-only IdPs without OIDC (for example GitHub OAuth apps;
  needs a userinfo-based identity, scheduled with M5).

## 10. M4 notes

- **A real-browser-only bug in M3, fixed.** Jack's sign-in pages sent
  `Referrer-Policy: no-referrer`. Under the Fetch spec, a form POST under that
  policy carries `Origin: null`, which the CSRF check (correctly) rejects, so
  Jack's own API-key and consent forms were refused in real browsers. The M3
  scripted browser set `Origin` itself and never saw it. The pages now send
  `same-origin`, and `Origin: null` is still refused. The Playwright suite
  (real Chromium) now covers these pages, so this class of bug fails CI.
- **One origin, many projects.** Locally (and for self-hosting), projects
  live under paths, and each authorization server's issuer is
  `<origin>/p/<slug>`, with discovery documents at the RFC 8414 / RFC 9728
  path-inserted locations. Sign-in cookies are scoped to the project's path,
  and tokens carry the project's MCP URL as audience. A token for one project
  is refused by another, and there's a test for that. Hosted will still use
  one host per project.
- **Ports.** Fixed ports would have made two worktrees clash.
  Per-worktree stable ports, `.jack/run/*.json` discovery and `${VAR}` in
  `jack.yaml` replace them (USAGE.md, *Ports and worktrees*).
- **Build hygiene.** `dist/` in `apps/jack-api` and `packages/jack-auth`
  once held output built from source that is not in this worktree (a
  `data-plane.js` and a different API, built 2026-11-09 22:13). It was
  rebuilt from source. The stray extra files in `apps/jack-api/dist/`
  (`data-plane.*` is now a real module, `keys.*` is not) are git-ignored and
  harmless, and can be deleted.
- **"Empty dashboard" report (2026-11-11), fixed.** In the founder's main checkout the M4 source was present but `dist/` was from M2 (dist is git-ignored, so new source never updates it, and `pnpm jack` ran dist directly). The old server served the new `index.html` but 404ed `/app.js` and `/style.css`: an unstyled page with a dead link. Now every launch script runs `scripts/jack-ensure-built.mjs` (rebuilds when source is newer than dist; ~50 ms when fresh), and the page explains itself if its script does not load.
- **Operator accounts and sessions: done 2026-11-11.** `jack serve
  --accounts` (shared `@graphmind-ai/accounts`, `packages/accounts`): sign-up,
  sessions, personal API tokens, projects owned per account; see
  `docs/jack/USAGE.md` → Accounts. Local without the flag stays open or
  key-protected.
- **Not yet in the dashboard:** git sync (the dashboard opening PRs),
  toolset editing (toolsets come from `jack.yaml`), and per-tool response
  shaping (`pick`/`maxBytes` are set in `jack.yaml`).

## 11. M5 notes

- **Shared secret instead of JWKS.** §3.4 planned a per-project JWKS that
  the customer would generate and host. That is exactly the kind of work
  `link` mode exists to remove. One shared secret (≥ 32 chars) signs all
  three token kinds (HS256, each with its own `typ`), verification is offline,
  and the Python and Ruby ports are ~250 lines of standard library each.
  Trade-off: a compromised customer app can mint assertions for its own API
  (which it could already do), and rotation is a simultaneous change on both
  sides. Asymmetric keys stay a possible option for customers who ask.
- **Assertions carry scopes from the token**, not from the grant record, so a
  narrowed refresh narrows what the app sees. Replay protection is on the
  customer's side (60 s jti cache in the verifier); Jack mints a fresh one
  per call.
- **Interop is tested, not assumed:** the Node suite spawns the real
  `python3` and `ruby` when present, verifies Node-signed tokens there, and
  verifies their responses back in Node.
- **Issuer up front.** Link mode needs the customer app to know Jack's issuer
  before Jack starts; locally that is the worktree's stable preview port, so
  `dev` and `start` compute it. Hosted, it is the project's fixed issuer.
- **Not yet:** consent remembered per user + app (every sign-in asks), rotating
  the shared secret with an overlap window, and surfacing `grant_id` in the
  customer's audit logs beyond the middleware's return value.
